## 2. データ構造

### 2.1 手順の表

```rust
pub struct Kernel { entry: &'static str, pipeline: wgpu::ComputePipeline,
                    bindings: wgpu::BindGroup, groups: Groups }   // Groups：固定の数か、間接
pub struct Step   { pub stage: Stage, pub kernel: usize }         // kernel は Kernels の中の位置
pub struct Kernels { kernels: Vec<Kernel> }                       // 1 更新は Vec<Step>（608 個）
```

- module はプログラムごとに 1 つ（模型・流れの解法・輸送の分割の予定・鏡映の 4 つ）、pipeline は入口ごとに 1 つ。
  v2.20 は 128 個の Kernel がそれぞれ module と pipeline を作っていた。
- 1 更新を、モジュールごとの `encode` の手続きではなく `Step` の列として持つ。製品は 1 つの pass に流し、道具は
  同じ列を段階ごと・kernel ごとに分けて測り、任意の Step の前後で書き出し、1 つだけ再生する。
- kernel は少しずつ作れるようにする（読み込み中の画面を出すため。下の 4.3）。

### 2.2 バッファ

寿命で二つ。**状態**は保存して回帰で比べ、**作業**は保存も比較もしない（段取り 4 で作った形。計画では六つに分ける
つもりだった。変えた理由は「段取り 4 の結果」）。

| バッファ | 中身 | 寿命 |
|---|---|---|
| `cells`（96 B × セル） | 四相の量、運動量、粒子の応力、粉、堆積 | 状態 |
| `geometry`（vec4 × 26 行） | 識別子ごとの気体の量と平面、接触の当てはめ、最後の応力の解法のときの開口と状態、板の牽引力、堆積の占有と通路 | 状態 |
| `faces`（160 B × 面）・`terrain` | 面の応答と開口、堆積の列 | 状態 |
| 流れ関数・`strata`・`labels` | 次の解法の初期値、堆積の層の記録、泡の付け直し（膜の計数、セルの語、泡の記録） | 状態 |
| `scratch`（vec4 × 50 行） | 上の砂（歯・本体・柱・栓）、粒子圧の掃引、一回目の射影の面の速度、輸送のグループと気体の流束、容量 | 作業 |
| `grain_works`（48 B × セル） | 粒の拘束の作業値 | 作業 |
| `transport`・`members`・`schedule`・`arrival`・`gaps`・接触の当てはめの一覧・流れの解法の行列と作業 | 流束、グループの所属、分割の予定、ほか | 作業 |
| `table`・`cfg`・流れの解法の階層 | 抵抗の表、格子と重力、多重格子の段 | 定数 |

- **状態**は `Buffers::state` の 7 本。これだけを別の模型へ渡せば、続きがビット単位で同じになる（裏返しの途中の
  進み具合は模型の側にあり、バッファには無い）。
- **作業**は、1 つの更新の中で、書いてから読む。次の更新へは何も残らない。
- `geometry` と `scratch` の行は `src/model/rows.rs` の一覧で決まる：使い道の名前と行数を並べ、最初の行はそれまでの
  行数の和。二つの使い道が同じ行に重なることが、構造上起きない。シェーダーの定数 `NAME_ROW` とバッファの大きさも
  同じ一覧から出る。
- kernel が束縛するバッファは、WGSL の変数名で決まる（`uses.rs` の表）。テストが naga でシェーダーから同じ表を作り直して
  比べ、1 つの入口が storage buffer を 8 本（WebGPU の保証）より多く使わないことも見る。いまの最大は 7 本。

### 2.3 シェーダー

`断片 ＋ 定数 → ループの書き下し → プログラムごとの module → 入口ごとの pipeline`

- module はプログラムごとに 1 つだけ作る。v2.20 の起動が重かったのは、同じプログラムの全文を kernel ごとに解析・検証
  し直していたためである（1 回 約 22 ms）。
- 入口に届く宣言だけを集める段は置かない。計画の時点では「wgpu の Metal 側は pipeline ごとに module の全関数を訳して
  コンパイルする」と読んでいたが、誤りだった（2026-11-19）：naga 30.0.1 は、入口が複数ある module から pipeline を
  作るとき、その入口に届くものだけに縮めてから MSL を書く（`process_overrides` の中の `compact`）。入口ごとに刈り込んだ
  module を作る実装も書いて測ったが、プログラムごとに 1 つの module と起動の時間が同じ（1.9 秒）だったので外した。
- 書き下しは最後の、スイッチで外せる段。ネイティブ（Metal）では v2.20 と同じ書き下しを使い、Web では測るまで
  外しておく。

## 3. 呼び出し順序

### 3.1 一生

```
起動     窓を出す → 読み込み中（kernel を数フレームに分けて作り、進み具合を描く）→ 初期化の pass → 実行中
毎 tick  下の 3.2
毎フレーム 下の 4.2
リセット  状態のバッファを書き直し、初期化の pass を流す（pipeline は作り直さない）
```

初期化の pass：`bed_geometry → bed_release → 界面（平面・接触・開口）→ prepare_bed_occupancy →
prepare_bed_passage → predict → prepare_grain_stress → prepare_stream → cache_contact → interface_tensor →
assemble → scale_interpolation・coarsen`

### 3.2 1 tick（8 ms）

```
1. 保留中のリセット・裏返しを適用
2. 裏返しを 1 更新ぶん進める（この更新の重力と横向きの加速度を書く。水平を過ぎたら鏡映の合図）
3. compute pass を 1 つ：鏡映があれば invert_cells → invert_stream → 界面の作り直し → clear_strata、
   そのあと 608 Step
4. 完了の通知で、進んだ更新と速さを数える
```

## 4. アプリ

### 4.1 操作パネルとビュー

- egui のパネルを一つ（v2.20 の下のメニューと左上の HUD を一つにまとめた）。既定は上の中央。
- 中身：裏返す、再生／停止、リセット、ビュー（単純・リアル・流れ）、時刻、速さ。細かい数値（開始からの平均、
  更新の数、水槽と格子、キーの一覧）は同じパネルの「Details」で開く。
- キー：F 裏返す、Space 停止、R リセット、V ビュー、H パネルを隠す／出す、P パネルの上下を切り替える。
- 格子の切り替え（G）は無くす。

### 4.2 1 フレームと、描画の頻度

```
絵（単純・リアル・流れ）は、テクスチャに描いて持っておく。大きさは窓に合わせる（view::picture_size）：
  窓に入るいちばん大きい 3:2。ただし 1440×960 より粗くはせず、画素が細砂ひと粒（110 µm）より細かくもしない（2727×1818 まで）
  描き直すのは「前に描いたあとに更新かビューの変更があって、前に描いてから 1/30 秒たったとき」だけ
窓の再描画（入力、パネル、大きさの変更）は、持っている絵を貼ってパネルを重ねるだけ
```

- 絵は 1 秒に 30 枚まで。いまは更新のたびに 1 枚（0.36 倍速で 1 秒に 45 枚）描いている。砂の動きは画面の上で
  1 秒に数十画素なので、30 枚で足りる。更新が 1 秒に 30 回より遅いときは、更新ごとに 1 枚になる。
- パネルの操作は絵の頻度と関係なく、入力のたびにすぐ再描画する（絵は描き直さないので軽い）。
- mikage の設定は、固定刻みの tick（8 ms）と、要るときだけの再描画。提示と、同時に流す提出の数は mikage の既定のまま
  （描けたフレームから提示する Immediate、提出は 8 つまで）。計画では「VSync の提示」（フレームを 1 つずつ流す）と
  していたが、測って替えた（「段取り 2 の結果」の窓の速さ）。30 という数は定数一つ（`PICTURE_INTERVAL`）で変えられる。
- 絵は、描いた枚数の履歴によらない（更新のたびに描いても、確かめる時刻にだけ描いても、同じ画素）。

### 4.3 読み込み中の画面

- 窓をすぐ出し、模型を 1 フレームあたり 30 ms ぶんずつ組み立てる（抵抗の表の帯、バッファ、kernel を 1 つずつ）。
  そのあいだ、何をしているかと進み具合のバーだけの画面を描く。模型ができたらビューを作り、更新を始める。
- kernel が全部できたところで 1 フレーム描いてから、最初の仕事を GPU に渡す。ブラウザは pipeline をそのときに
  コンパイルするので（wgpu の Web 側は作る呼び出しがすぐ返る）、その数秒のあいだ「kernel をコンパイル中」が出ている。
- Web では、最初のフレームが出るまで `index.html` の「Loading…」を出しておく（mikage の例と同じ）。

### 4.4 Web

- `trunk build` で同じ実行ファイルを WASM にする。操作口（agent）と道具はネイティブだけ。
- 時刻は `web-time`、場面は `include_bytes!`。WebGPU の既定の上限（storage buffer 8 本、workgroup 256 スレッド）の
  中で動く作りはいまと同じ。
- 段取りの 0 で空のアプリが Chrome で動くこと、2 で模型が動くことを確かめた（結果は「段取り 2 の結果」）。
- ループの書き下しは Web では入れない（測って、得が無かった）。

## 5. 検証

1. **v2.20 との照合**：v2.20 のバイナリが 30 秒ごとに保存した状態（旧 repo の `artifacts/local/limits` の
   `loops2-life`・`adopt-life2`）と、状態をビット単位で比べる。ずれた更新は Step ごとに再生して、最初に違う
   kernel を特定する。写す途中の確認には、feature で標準格子にして `adopt-std` と比べる（2 倍速い）。
2. **回帰**：状態と、単純・リアルの画素のビット一致（0・1・5 秒と、60 秒まで）。基準は 1 が通った時点で取る。
3. **保存と復元**：保存 → 復元 → 続きが、止めずに走った続きと一致すること。
4. **見た目の変わる変更**（窓の画素で描く、粒の見え方、あとの美麗さの調整）：同じ時刻の前後の絵でユーザーが判断する。
5. **丸めの変わる変更**：いまと同じ手順（丸め違いの起動 10 本ずつ、一生の読み取り）。読み取りは `tools` の `lives`。

GPU を使う照合は、ユーザーがアプリを見ていないときに流す。流すときは知らせる。

## 6. 段取り

0. **土台**：フォルダ、ツールチェーン、ignore、空のアプリ（窓・パネル・読み込み中の画面）がネイティブと
   `trunk build` の両方で動くところまで。→ 報告
1. **模型の移植**：バッファは v2.20 の並びのまま、kernel を写し、手順の表で組む。
   検証の 1 が通るまで。起動の時間を測る。→ 報告
2. **アプリ**：tick、裏返し、作り直さないリセット、三つのビュー、描画の頻度、Web で動かす。回帰の基準を取る。
3. **窓の画素で描く**：絵の大きさを窓に合わせ、粒の見え方を画素の大きさから決める。1440×960 では基準と一致。
   ほかの大きさの絵を見せる。
4. **バッファの分割**：まとまりごとに一つずつ、そのたびに照合。
5. **リアルの調整**：落ちる砂を粒で描く、上の砂の縁をくっきり描く、ほか。一つずつ、前後の絵で。

## 段取り 1 の結果（2026-11-19）

模型は `src/model` にある。バッファは v2.20 の並びのまま、1 更新は 24 段階・608 step の表で、段階ごとの数は 3.3 の表と
同じである（`cargo run --release --example run -- OUT --steps 0` が表を出す）。

**v2.20 との照合**（M1 Max、macOS 27.2.1、wgpu・naga 30.0.1、Rust 1.95.0。照合の道具と走行は `records/stage1/`）

| 何を | 比べた先（旧 repo） | 結果 |
|---|---|---|
| 0・1・5・15・30・60 秒の、比べる 8 本のバッファ | 回帰の基準 `tests/baseline/manifest.json` のハッシュ | 48 個すべて一致 |
| 起動からの一生（1200 秒、15 万更新）：30 秒ごとのセルと堆積の列 | v2.20 の走行 `loops2-life` の 40 回の保存状態 | 80 ファイルすべて一致 |
| 同じ一生の 1200 秒の時点：8 本と strata の全体 | `loops2-life/state-01200` | 9 本すべて一致 |
| その終わりを裏返した二回目の一生（v2.20 の 1200 秒の状態を読み込み、2400 秒まで）：30 秒ごとのセルと堆積の列 | v2.20 の走行 `adopt-life2` の 40 回の保存状態 | 80 ファイルすべて一致 |
| 二回目の一生の終わり（2400 秒）：8 本と strata の全体 | `adopt-life2/state-02400` | 9 本すべて一致 |

## 段取り 3 の結果（2026-11-19）

絵の大きさが窓に合うようになった。1440×960 より大きい窓（1 倍のディスプレイで幅 1440 画素を超える窓、Retina で
その半分を超える窓）では、絵が窓の画素数で描かれて、粒と泡の縁がくっきりする。それ以下の窓は、これまでと同じ絵である。

- **粒**：リアルのビューは、止まった砂を粒の場所（細砂ひと粒ぶんの升目）ごとに白か黒で描く。画素の色は、その画素に入る
  粒の平均で、画素を「粒の場所ひとつぶんより離れない点」で調べる（一辺の点の数は、画素の幅を粒の場所の幅で割って
  切り上げた数）。1440×960 では v2.20 と同じ 4 点になるので、回帰の絵は変わらない。四捨五入ではなく切り上げにしたのは、
  窓の大きさを変えていくときに粒の濃淡が段になって変わるところを、描く範囲の端（画素＝粒ひとつ）にだけ置くためである。
- **1440×960 より粗くは描かない**：実際の 1 倍のディスプレイの窓（720×480）で 720×480 に直接描いた絵は、粒は
  同じに出たが、筏の泡が灰色にぼやけた。リアルは泡の縁の光り方を「画素の中では輪郭がまっすぐ」として積分していて、
  画素がセルの 3/8 まで広がると、セル 1〜2 個の泡では成り立たない。小さい窓は、1440×960 の絵を縮めて見せる
  （段取り 2 と同じ。実際の窓の絵は 5・15・60 秒で段取り 2 と画素単位で一致）。
- **費用**（Photoreal の絵 1 枚の GPU 時間。60 秒と 300 秒の状態を 200 枚ずつ続けて描いた）：

  | 絵の大きさ | 60 秒の状態 | 300 秒の状態 |
  |---|---|---|
  | 720×480 | 1.67 ms | 1.75 ms |
  | 1440×960 | 1.85 ms | 2.01 ms |
  | 2160×1440 | 2.72 ms | 3.11 ms |
  | 2727×1818 | 3.51 ms | 4.09 ms |

  毎秒 20 枚なら GPU の時間の 2% である。
- **確かめたこと**：`check` は、絵の大きさを途中で変えたビューが、最初からその大きさで作ったビューと同じ絵を描くことも
  見る（窓の大きさの変更が頼る経路）。1800×1200 の窓で起動した実際のアプリが持っている絵は、道具が同じ大きさで

  feature `fixed-picture` を付けてビルドすると、どの窓でも 1440×960 の絵を窓に合わせて拡大・縮小する（v2.20 と同じ）。

**なぜ作り直したか**：v2.20 のリアルは、識別子ごとの距離場をセルの中心で作って泡を描いていた。筏では 1 つのセルに
いちばん多い識別子が気体の 8〜9 割、残りがほかの識別子の切れ端として入っていて、識別子ごとの場はセルの中心のまわりの
小さな塊に割れた。筏の気体の大半は泡として描かれず、その場所は砂の色で塗られていた（「上の砂の下の縁の段々」は
空気の層の下の縁だった）。割れ残りの塊は、連続する絵のあいだで輪郭の画素の 6.6〜8.5% が入れ替わり、細かく振動して見えた。

**描き方**（`src/view/sketch.wgsl`、`src/view/photoreal.wgsl`。規則の理由はそれぞれのコメントにある）

- **スケッチ**：絵を描く前に、計算の kernel 2 つがセルごとに「絵がそこに描くもの」を書く（48 B × セルが 2 本）。
  一つ目はセル自身の値（気体の合計と、多いほうから 2 つの識別子。堆積の外の砂の体積・速度・止まっている度合い）、
  二つ目はまわりのセルを見て決まるもの（その砂が止まった砂の体のものか、粒で見せる砂か）。セル全体に関わる判断は
  ここで 1 セルに 1 回だけ行い、画素のシェーダーは補間するだけにする。
- **場**：気体も砂も、セルの値を 2 次の B スプラインで補間した滑らかな場として描く。セルの縁に角ができず、セルより細かい
  形は出ない。場が半分になる高さが、セルを満たしているものの輪郭である（まっすぐな面なら、ずれはセルの 10 分の 1 以内）。
- **砂**は三つを重ねる。落ちる砂や薄く積もった砂は、粒の場所ごとに粒を見せ、粒の模様を砂の速度で運ぶ（0.5 秒ごとに
  敷き直す二つの模様を画素ごとにずらして入れ替え、1 コマの露光のあいだは進む向きにだけ流す）。黒い粒を見せる確率は
  「粒の断面が視線をふさぐ割合」（視線が横切る粒の深さ t = 1.5 × 隙間 × 体積率 ÷ 粒径 に対して 1 − exp(−t)）、
  白い粒を見せる確率は下の「薄い砂の白さ」で決まる。止まって詰まった砂の体は、セルの
  濡れた部分を半分満たすところまでを、はっきりした面で描く。堆積はこれまでどおり層の記録から描く。体と堆積の粒は
  ガラスに対して止めて描く（ゆっくり動く砂の模様まで運ぶと、速度のわずかな揺れが模様の飛びになる）。
- **体の面に乗った層**：模型は、上の砂の上面を滑り落ちる砂を、面の上 3〜5 セルに広がった薄い雲として運ぶ
  （下の「模型について分かったこと」）。セルにあるとおり粒で描くと、斜面の上の水に粒が漂って見える。そこで、
  体の面から 8 セル以内に途切れずに続く砂は、面のセルに、体の砂として描く。それより高くまで続く砂は、体の上に
  落ちてくる筋として、そのまま粒で描く。
- **薄い砂の白さ**（二回目）：白い砂はシリカとガラス玉で（特許の配合）、水の中の一粒は光をほとんどまっすぐ通す。
  球を光線で計算すると、散らした光の進む向きの余弦の平均 g は石英 0.90・ガラス玉 0.92・溶融シリカ 0.95 で、後ろ向きへ
  返すのは当たった光の 1〜3% である（`records/stage5/grainoptics.py`）。砂が白いのは粒が何層も重なるからで、吸収のない
  層が暗い背景の前で返す光は k t / (1 + k t)（t は視線が横切る粒の深さ、k = (1 − g)/2 = 0.05）。堆積（t = 8）の白さを
  1 とすると、薄い砂は粒 1 枚あたり 0.175 である。絵は、この白さになる確率で、堆積と同じ白さの粒を見せる（薄いところでは
  約 6 粒に 1 粒、隙間を満たすところでは全部）。白い砂から離れた粉も、同じ式の白さで水を白くする。白さの式と k は
  物理から決まり、「何粒かに 1 粒を堆積と同じ白さで見せる」ことは描き方の約束である。どの粒も 6 分の 1 の白さで描く案は、
  平均は同じだが、筋が霞になって粒が見えないので採らなかった。一回目は、視線が出会う粒をどれも堆積と同じ白さで描いていて、
  落ちる砂が、それが作る堆積の約 6 倍白かった（ユーザーの指摘）。
- **泡**：各点の泡は、そこでいちばん多い識別子である。泡の輪郭は、気体全体の場が
  1/2 + (1 − w)(1 − 3w)/2 になる高さに引く（w は、その識別子と二番目の識別子の気体の差を和で割ったもの）。
  二つが等しいところ（w = 0）では、気体で埋まったセルにだけ泡があり、そこが膜になる。膜が気体全体の輪郭に出会う
  ところでは、泡はそれぞれ丸く膜へ回り込み、二つの丸みのあいだに水か砂が見える（泡どうしのすき間、Plateau border）。
  膜と膜のあいだでは、輪郭は半分の高さより外へ、丸みが削ったぶんだけ膨らむ（式の w についての平均が 1/2 になるように
  選んである）。膨らみは、気体全体の半分の高さからセルの 4 分の 1 までに限る（薄く広がった気体が点として出るのを防ぐ）。
  泡の肩の丸みは模型のセルより細かく、セルの値だけからは出ない。この規則は、丸みを足して、面積を模型に合わせるための
  描き方の約束である。
- **泡の縁**：隙間の半分の深さのメニスカスが、スタジオの光を反射・屈折する（v2.20 と同じ計算）。背景の暗い板を
  水槽の 8 cm 後ろから 30 cm 後ろへ下げた：縁で 30 度以上曲がった光が板の外の明るい面を見て、縁が白い線になる。
  縁の反射には、隣の砂粒を映さない：実物では砂に接した縁は砂の色に溶けるが、それでは白い砂の下の泡の輪郭が
  消えるので、線を残した（描き方の約束）。線の太さは、輪郭の向きと水槽の中の位置で変わる（曲がった光が板の縁を
  越えるかどうか）。
- **流れのビュー**：明るさを、速さの平方根（25 mm/s で最大）にした。これまでの対数（0.01〜10 mm/s）では、1 mm/s の
  水が筋の 3 分の 2 の明るさで、速さの違いが読めなかった。上の砂のゆっくりした動き（0.1 mm/s）は見えなくなる。

## 模型が v2.20 と違うところ

計画では、模型を変えないとした。そのあとユーザーの判断で入れた模型の変更を、ここに並べる。物理の仕様は旧 repo
（report.md、docs/physics）にあり、そこに書かれているのは v2.20 である。

### 粉を放す規則の、沈む速さ（2026-11-20）

- **規則**：触れ合った砂のあいだを、水が白い粒の沈む速さより速く抜けるとき、その砂の粉が自由になる（旧 repo の
  docs/physics/bed-transport.md「粉は粒に結びついている」）。その沈む速さを、粒にかかる重力の全体（ガラスに沿った成分、
  隙間を横切る成分、揺すりの横の成分）で測る。v2.20 は、ガラスに沿った成分と揺すりの成分だけで測っていた
  （`src/model/transport/powder.wgsl` の `free_powder`）。
- **理由**：粒の重さは、絵を倒しているあいだも変わらない。ガラスに沿わない分は、粒を下の板に押し付けている。この規則は
  「水の抗力が粒の重さを越えると、塊が引き裂かれる」という意味なので、比べる相手は重さの全体である。
- **v2.20 で起きていたこと**：絵を倒すと、ガラスに沿った重力は g|cos θ| に減り、水平になる更新では単精度で
  5.7×10⁻⁵ g になる。沈む速さがほぼ 0 なので、その 1 更新で、少しでも動いている触れ合った砂の粉がすべて自由になった。
  起動からの一生の 300 秒の状態を裏返すと、上の砂の粉 3846 mm³ のうち 3697 mm³（96%）が自由になり、開いた水の
  自由な粉の割合は、裏返し始めて 5・15・35 秒後に 2.1×10⁻⁴・2.8×10⁻³・4.0×10⁻³ になった（実物の動画は 10⁻⁴ 未満）。
  旧 repo で開いていた課題「一生の途中で裏返すと、水が 6 分ほど霞む」の原因である。起動のときは、水平になる更新で
  砂がまだ堆積として止まっていて、放す粉が無かった。
- **確かめたこと**：同じ裏返しで、自由な粉は 0.3〜0.5 mm³ のまま、開いた水の自由な粉の割合は 5・15・35・60 秒後に
  0.6×10⁻⁵・1.4×10⁻⁵・1.3×10⁻⁵・1.0×10⁻⁵ で、水は澄んでいる。満杯を越えるセルも非数も無い。`check --full` は、
  基準を変えずに全 70 項目が通る：起動からの一生は v2.20 と同じ結果のままで、変わるのは、砂が上に残っているときに
  裏返した場合だけである（回帰の走行には、その場合が無い）。走行と道具は `records/research/`
  （`turn300-main`・`turn300-powder`、`powder.py`）。
- **どちらの規則でも見えたこと**（調べていない）：300 秒で裏返して 35 秒後、床へ落ちた砂の中に、暗い袋と縦の割れ目が
  ある（下敷きになった水か泡）。60 秒後には閉じている。
